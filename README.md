# 财务场景 AI 输出质量评测工具

用 Python 自动检验大模型在财务场景下的回答**准不准、会不会编数字**，并比较不同提示词写法的效果。

> 数据全部为模拟数据，不涉及任何公司的真实信息。

## 为什么做这个

财务部门推广 AI 工具时，最常被问的是两个问题：

1. **AI 算的数对不对？**
2. **AI 写的报告里，有没有编出来的数字？**

靠人工抽查很难给出有说服力的答案。这个工具做的事很简单：**先用程序算出标准答案，再让 AI 回答同样的问题，逐条比对，最后给出准确率。** 每次修改提示词或更换模型后重跑一遍，就能看到效果是变好了还是变差了。

## 评测内容

| 场景 | 对应的财务工作 | 测什么 | 怎么判对错 |
|---|---|---|---|
| 账龄问答 | 共享核算会计：按月出具应收账龄分析 | 10 道计算题，比如逾期总额、逾期占比、逾期最多的客户 | 标准答案由 pandas 计算，金额误差不超过 0.5% 算对 |
| 账龄摘要 | 同上，写分析文字 | 让 AI 写 150 字摘要，每版提示词跑 3 次 | 摘要里的每个金额和比例，都要能在原表或汇总结果中找到 |
| 返利提取 | 采购财务：审核供应商返利条款 | 6 份合同，每份提取 5 个字段 | 按字段比对人工标注的答案；R04、R06 故意设置了陷阱 |

提示词共有三个版本（见 `prompts.py`）：

- **v1**：简单直接的问法，代表多数人的日常用法
- **v2**：加入角色、数据约束和输出格式，例如“只能使用表格数据”“原文没有写的填未约定”
- **v3**：根据 v2 的评测结果修正。账龄问答修正了答案格式，摘要改为由程序先算好数字。返利场景 v2 已基本达标，没有做 v3

## 评测结果（模型：deepseek-chat，2026 年 11 月）

| 指标 | v1 简单问法 | v2 加约束 | v3 迭代后 |
|---|---|---|---|
| 账龄问答准确率（10 题） | 50% | 70% | **100%** |
| 摘要中找不到出处的数字占比 | 43%（16/37） | 65%（13/20） | **0%（0/35）** |
| 返利字段可直接入台账的比例（6 份合同 × 5 个字段） | 80% | **97%** | — |

完整报告见 `results/评测报告.md`，每道题、每篇摘要、每个字段的明细见 `results` 文件夹中的 CSV。

## 三轮迭代发现了什么

**第 1 轮：v1 → v2，加入角色、数据约束和输出格式**
- 返利提取：可直接入台账的比例从 80% 提升到 97%。人工复核发现，v1 的内容大多是对的，问题在于格式不统一，比如有效期写成“两年，自 2026 年 7 月 1 日起”。v2 统一了格式，下游程序可以直接使用。
- 账龄问答：计算题全部答对，但出现了副作用。v2 要求“金额写纯数字”，模型在问客户名、销售名时也回答了数字。

**第 2 轮：发现模型加总经常算错**
- 让模型直接读表写摘要时，单个客户的数字它都能抄对，但应收合计、逾期合计这类加总，6 次结果各不相同，而且全都是错的。正确的应收合计是 1267.0 万，模型写过 1094 万、921.0 万等。
- v2 要求“万元保留 1 位小数”，反而让错误的数字看起来更精确、更容易被相信。

**第 3 轮：v3 修正**
- 账龄问答：明确规定“问金额答数字，问名称答名称”，准确率达到 100%。
- 摘要：改为先用 pandas 算好合计和排名，模型只负责组织文字。找不到出处的数字降到 0。人工逐句核对 3 篇摘要，客户、销售和金额的对应关系全部正确。

**结论：在财务场景中，数字应该由程序计算，大模型负责理解和表达；提示词的每一次修改，都需要用固定的测试集重新验证。**

## 怎么运行

**1. 安装依赖**

```bash
pip install -r requirements.txt
```

**2. 设置大模型接口**（任何兼容 OpenAI 格式的接口都可以，以 DeepSeek 为例）

Mac / Linux：
```bash
export LLM_BASE_URL=https://api.deepseek.com
export LLM_API_KEY=你的密钥
export LLM_MODEL=deepseek-chat
```

Windows PowerShell：
```powershell
$env:LLM_BASE_URL="https://api.deepseek.com"
$env:LLM_API_KEY="你的密钥"
$env:LLM_MODEL="deepseek-chat"
```

> 接口地址和模型名称请以服务商官网的最新文档为准。

**3. 先空跑一遍，确认流程没问题**（不调用接口，不花钱）

```bash
DRY_RUN=1 python run_all.py
```

Windows PowerShell 写成：`$env:DRY_RUN="1"; python run_all.py`。空跑完后执行 `Remove-Item Env:DRY_RUN`（Mac 上执行 `unset DRY_RUN`），再正式运行。

**4. 正式运行**（共调用约 38 次接口）

```bash
python run_all.py
```

结果保存在 `results` 文件夹：`评测报告.md`，以及三张明细表。

## 文件说明

| 文件 | 作用 |
|---|---|
| `run_all.py` | 一键运行全部评测，生成报告 |
| `eval_aging.py` | 账龄问答和摘要的评测逻辑 |
| `eval_rebate.py` | 返利条款提取的评测逻辑 |
| `prompts.py` | 三版提示词模板（v1、v2、v3） |
| `llm.py` | 调用大模型接口，带失败重试 |
| `utils.py` | 金额换算（“12.5万”转成 125000）和误差比较 |
| `aging.csv` | 模拟应收账龄表，12 个客户 |
| `rebate_contracts.csv` | 6 份模拟返利条款和标准答案 |

## 设计要点

- **数字由程序计算，不交给 AI。** 标准答案全部由 pandas 算出，避免人工填写出错。
- **“找不到出处”不等于“一定是错的”。** AI 自己合理推算出的数字，比如某个客户的逾期占比，如果不在预设的汇总范围里，也会被标出来。所以这项指标的用途是**提示人工重点核对哪些数字**。
- **故意设置陷阱。** R04 是按件返利，没有比例和金额门槛；R06 大部分内容没有约定。这两份专门用来检验 AI 会不会把原文没有的内容编出来。

## 局限

- 样本量小（10 道题、6 份合同），每个版本只跑了一轮，结果只能说明趋势。实际使用前需要用真实业务数据扩充测试集。
- 模型每次的表现会有波动：两轮运行中，v1 答错的题不完全相同。
- “找不到出处”的检查只核对数字本身，不核对数字和客户的对应关系。比如“C12 的 38 万全部超过 90 天”这种张冠李戴的说法，程序检查不出来，摘要仍然需要人工抽查。
- 返利字段用的是严格匹配，比如“另行协商”没有算作“未约定”。所以这项指标衡量的是“能否直接录入台账”，不是“内容是否正确”。没通过的项已经全部列在报告里，供人工复核。
